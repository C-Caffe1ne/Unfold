## 1. 확정 사항과 계획 전제

| 항목 | 기준 |
|---|---|
| 사용 흐름 | 무료 다운로드 → 앱 실행 → Google 회원가입/로그인 → 구매 권한 확인 → 미구매자 결제 → 사용 |
| 체험 | 3일 무료 체험 제외. 체험 시계·만료·재설치 방지 기능도 개발하지 않는다. |
| 가격 | 국내 4,900원 / 해외 US$3.99. 환율로 서로 계산하는 하나의 가격이 아니라 독립 가격으로 다룬다. |
| 세금 | 결제 시 별도 추가. Lemon Squeezy 스토어의 tax-inclusive pricing을 끈다. 최종 합계는 구매자의 결제 주소에 따라 계산한다. |
| 상품 | 이전 단일 앱 일회성 구매 방향을 유지하는 계획. 구독·기능별 등급·별도 펫 상점은 범위 밖이다. |
| 데이터 관리 | Supabase Auth, PostgreSQL, Edge Functions 사용 |
| 도메인 | 작업 중. 개발·테스트와 정식 도메인 전환을 분리한다. |
| 출시 준비 | 사전 체험 사용자 모집이나 사용성 데이터 확보를 개발 착수 조건으로 두지 않는다. |
| UI 진행 | 기존 디자인 시스템으로 시안을 먼저 보여주고 확인 후 제품 UI에 적용한다. 기능 설명 문구를 임의로 늘리지 않는다. |

‘유저 데이터 확보 없이’의 세부 의미는 확인 중이다. 이 계획은 Google 로그인·구매 복원에 필요한
최소 계정·주문 정보 저장을 전제로 한다. 행동 분석, 마케팅 목록, 휴식 기록 수집은 제안 범위에 없다.
계정 정보도 전혀 저장하지 않는 요구라면 기존 Google 로그인·구매 복원 흐름부터 재설계해야 한다.

기존 `business-model.md`, `product-direction.md`, `development-plan.md`, `mvp.md`와 웹 목업에는
3일 체험·미확정 가격·이전 기능 설명이 남아 있다. 이번 결정과 충돌하는 기획에는 이 문서와 최신
사용자 요청을 적용한다. 기존 문서·웹의 정리와 단계별 준비 상태는 아래 10절에 기록한다.

## 3. 도메인 없이 진행할 수 있는 범위

| 실행 구간 | 지금 할 수 있는 일 | 필요한 외부 준비 |
|---|---|---|
| 로컬 개발 | 상태 모델, DB 마이그레이션, 권한 정책, API 계약, 가짜 응답 테스트, 화면 시안, 기존 데이터 보존 테스트 | 없음. 로컬 Supabase 실행은 CLI·Docker 등 개발 환경 준비 필요 |
| 개발 서버 연결 | Supabase 테스트 프로젝트, Google 테스트 사용자 로그인, 구매 권한 조회, 웹훅 수신 | Supabase 프로젝트·Google Cloud OAuth 설정 |
| 결제 테스트 | 테스트 주문·취소·환불·중복 알림·앱 구매 복원 | 선택한 결제사의 테스트 환경과 필요한 키 |
| 정식 공개 | 실제 결제, 정식 설치 파일 다운로드, 공개 Google 로그인 | 운영 설정·판매자 심사·운영 URL·정책 페이지·배포 검증 |

Google 인증은 Supabase 프로젝트의 인증 콜백과 개발용 localhost 반환 주소로 검증할 수 있다.
자체 도메인은 개발의 선행 조건이 아니다. 등록한 반환 주소만 사용하고, 테스트 사용자 범위에서
검증한다. [Supabase Google 로그인](https://supabase.com/docs/guides/auth/social-login/auth-google),
[반환 URL 설정](https://supabase.com/docs/guides/auth/redirect-urls).

Edge Functions는 Supabase 프로젝트의 HTTPS 주소로 제공되므로 웹훅 서버를 위해 자체 도메인을
기다릴 필요가 없다. 원격 결제사는 개발자의 localhost로 직접 웹훅을 보낼 수 없으므로 테스트
프로젝트의 공개 HTTPS 엔드포인트를 사용한다. [배포 문서](https://supabase.com/docs/guides/functions/deploy).

도메인이 준비되면 웹 운영 URL과 OAuth 허용 URL·결제 반환 URL을 환경 설정으로 교체하고 다시 검증한다.
Google·결제사 공개 심사 요건 충족 여부와 도메인 보유 여부는 별도로 확인한다.

## 4. 가격을 지키기 위한 결제사 선택

**국내 4,900원 결제를 기존 Lemon Squeezy 하나로 보장한다고 전제하지 않는다.**
공식 문서는 원화 표시를 지원하지만 실제 거래는 USD로 처리한다고 설명한다. 따라서 ‘4,900원 표시’와
‘4,900원 원화 청구’는 동일하지 않다. 스토어 통화 설정도 따로 존재한다.
[Lemon Squeezy 통화 문서](https://docs.lemonsqueezy.com/help/payments/currencies).

P0의 선행 기술 검증은 다음과 같다.

1. 국내는 4,900원 원화 결제 가능한 PG를 검토한다. 토스페이먼츠를 후보로 두되 계약을 확정하거나 신청하지 않는다.
2. 해외는 기존 Lemon Squeezy US$3.99 일회성 결제를 후보로 유지한다.
3. 단일 PG로 국내·해외 결제를 모두 운영할 수 있는지도 비교한다. 토스페이먼츠 문서상 KRW·USD는 별도
   MID 구성이 필요하므로 실제 계약 가능 여부·수수료·운영 부담을 확인한 뒤 선택한다.
4. 결제사와 무관하게 구매 권한은 같은 Supabase 계정에 연결한다. 두 결제사 구현을 무조건 선행하지 않고,
   공통 주문·권한 계약을 만든 뒤 선택한 결제사만 연결한다.

[토스페이먼츠 테스트 환경](https://docs.tosspayments.com/guides/v2/get-started/environment),
[해외 결제 및 통화별 MID](https://docs.tosspayments.com/guides/v2/learn/foreign-payment).

국내/해외 분류 기준은 출시 전에 확정한다. 제안은 결제 국가 기준이며 앱 언어·IP는 표시 힌트로만 사용한다.
가격은 서버가 관리하는 상품 코드로 결정한다. 클라이언트가 보낸 금액을 그대로 결제하지 않는다.
결제 국가 변경 시 가격 적용 방법은 선택한 결제사의 실제 동작으로 검증한다.

4,900원·US$3.99가 세금 포함 최종 결제액인지 상품 기준 가격인지도 결제 UI 적용 전에 확정해야 한다.
사용자 가격을 임의로 바꾸지 않는다. 테스트 주문에서 표시액·승인액·환불액·정산 수수료를 확인한다.

## 5. 최소 데이터 및 신뢰 경계

| 저장 위치 | 저장할 정보 | 제한 |
|---|---|---|
| Supabase Auth | 사용자 UUID, Google 연결 정보, 인증에 필요한 기본 정보 | 자체 비밀번호·별도 프로필 설문을 만들지 않는다. 공급자가 보관하는 이메일 등은 별도로 고지한다. |
| `products` / `prices` | 단일 앱 상품, KRW 4900·USD 399의 최소 통화 단위 금액, 시장, 결제사 상품 매핑 | 가격 수정은 서버 관리 권한만 허용 |
| `orders` | 계정 UUID, 내부 주문 ID, 결제사 주문 ID, 상태, 통화·금액, 구매·환불 시각 | 카드 정보·청구 주소를 앱 DB에 복제하지 않는다. |
| `entitlements` | 계정 UUID, 앱 상품, 유효/회수 상태, 근거 주문 | 사용자 직접 생성·수정 금지. 유효 주문이 하나라도 있으면 권한 유지 |
| `payment_events` | 공급자 이벤트/중복 판정 키, 주문 ID, 처리 상태·재시도 정보 | 원문 전체·비밀키·인증 토큰을 로그에 남기지 않는다. 중복·순서 역전 처리용 |
| 사용자 기기 | 설정, 휴식 기록, 커스텀 펫 파일 | 기존 로컬 저장 유지. 이번 출시에는 클라우드 동기화 없음 |
| OS 보안 저장소 | 로그인 세션과 구매 권한 검증에 필요한 비밀 정보 | 일반 설정 JSON과 분리. macOS·Windows별 저장·삭제 검사 |

RLS로 계정별 접근을 분리하고, 주문·권한은 검증된 서버 처리만 쓰도록 한다. `service_role` 키와
결제사 비밀키는 앱·웹 번들에 넣지 않는다. [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

서버 작업은 인증된 `create-checkout`, `get-entitlement`, 결제사별 서버 승인/웹훅 처리로 나눈다.
Supabase JWT의 사용자 ID로 주문을 만들고 결제 결과는 내부 주문을 통해 같은 계정에 연결한다.
결제 이메일이 로그인 이메일과 다르더라도 잘못된 사용자에게 권한을 주지 않아야 한다.

웹훅은 공급자 방식으로 진위를 검증하고 주문·상품·금액·통화·테스트/운영 구분을 확인한다.
반환 페이지나 요청 본문의 `isPaid` 값은 구매 증거로 쓰지 않는다. 공급자별 서버 조회·승인 절차를
따르며, 실패 재시도와 중복 처리를 트랜잭션으로 보장한다. 환불 뒤 늦게 온 구매 알림이 권한을
되살리지 않게 하고, 복수 유효 구매 중 한 건 환불만으로 전체 권한을 회수하지 않는다.
[Lemon Squeezy 웹훅](https://docs.lemonsqueezy.com/guides/developer-guide/webhooks),
[토스페이먼츠 결제 승인 API](https://docs.tosspayments.com/reference).

## 6. 앱 상태와 화면 설계

```text
앱 실행 → 저장된 세션/구매 권한 확인
  ├─ 미로그인 → Google로 계속하기 → 구매 권한 확인
  ├─ 미구매 → 가격·구매 버튼 → 브라우저 결제 → 서버 구매 확인 → 홈
  ├─ 구매 완료 → 홈 → 타이머·펫 시작
  └─ 통신 실패 → 유효한 기존 구매 증명이 있으면 오프라인 사용 / 없으면 재시도
```

- 최초 로그인·구매 활성화에는 인터넷이 필요하다. 무료 체험 상태는 만들지 않는다.
- 시스템 브라우저 인증과 PKCE를 사용한다. 앱이 생성한 검증 정보를 유지한 채 로컬 반환 주소에서
  인증 코드를 교환하는 흐름을 먼저 기술 검증한다. 포트 충돌·인증 취소·시간 초과·중복 실행도 처리한다.
- 화면 상태는 로그인, 브라우저 인증 대기, 미구매, 결제 확인 중, 사용 가능, 복구 가능한 오류로 나눈다.
- 별도 회원가입 폼·라이선스 키 입력·판매 대시보드는 초기 필수 범위에 넣지 않는다.
- 결제 도중 앱을 닫아도 서버에서 결제를 반영하고 다음 실행에 복원한다. 중복 구매를 유도하지 않는다.
- 로그인 세션 만료와 구매 권한 소멸을 구분한다. 통신 실패를 환불이나 미구매로 처리하지 않는다.
- 서명된 구매 증명의 캐시를 검토한다. 오프라인 허용 기간과 환불 반영 시점은 명시적으로 정한다.
  무기한 오프라인 사용과 즉시 환불 차단을 동시에 보장한다고 약속하지 않는다.
- 로그아웃·계정 변경 시 인증·권한 캐시를 분리하고 이전 계정 권한이 다음 계정으로 넘어가지 않게 한다.
  기존 로컬 기록·펫을 자동 삭제하거나 서버에 올리지 않는다.
- 자동실행·트레이·단일 인스턴스 활성화에서도 같은 권한 확인을 거친다. 잠긴 상태에서는 타이머와
  펫 알림이 시작되지 않는다. 유효한 구매자의 백그라운드 실행은 기존 동작을 유지한다.
- 개발용 가짜 권한·진단 우회는 운영 배포에서 외부 인자나 설정만으로 활성화할 수 없게 분리한다.

필요한 회귀 검사·Release 빌드를 실행하고, 상태 모델 테스트·서버 테스트·자동 캡처·실제 OS 입력을
분리해 보고한다. 구매 흐름은 자동 테스트나 화면 목업만으로 완료 처리하지 않는다.

## 8. 운영 전에 남은 결정

- 가격의 세금 포함 여부, 국내/해외 판정 기준, 결제사 및 실제 판매 계약.
- 1회 구매의 사용 기기 수와 업데이트 제공 범위. 초기에는 계정 권한 중심으로 설계하고 미정인 기기 제한을 임의 도입하지 않는다.
- 오프라인 권한 유효 기간, 재인증·환불 반영 방식, 고객지원·계정 삭제 요청 시 처리 기준.
- 기존 무료 개발 버전 사용자 혜택. 이미 배포된 무인증 앱은 새 서버만으로 잠글 수 없다.
- 계정·주문 정보 최소 저장에 대한 사용자 확인. 개인정보·환불·지원 정책 페이지는 실제 운영 방식에 맞춰 작성한다.

지금 착수할 첫 묶음은 **P0 가격·정책 정리 + P1 화면 시안 + P2의 DB/API 설계**다.
이후 Google 테스트 로그인과 테스트 결제를 연결한다. 도메인 완료 전에도 이 단계들을 진행할 수 있다.

## 9. 최초 계획 수립 당시 검증 범위

현재 코드·문서·공식 공급자 문서를 확인해 이 계획을 작성했다. 제품 코드와 기존 문서는 변경하지 않았다.
신규 계획 파일의 필수 결정 사항·저장소 참조·코드 블록·공백과 `git diff --check`를 검사했다. 앱 빌드·결제 테스트·실제 Google 로그인·외부 서버 생성은
이번 계획 작업에서 수행하지 않았다. 미리 있던 펫 동작 수정 및 미추적 아트 파일은 이번 범위 밖이다.
