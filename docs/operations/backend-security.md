# 백엔드 데이터 보안 운영

2026-10-11 기준. [적용·검증 결과](../validation/2026-10-11-backend-security.md).

## 접근 설계

| 데이터 | 접근 |
|---|---|
| 상품·가격 | 공개 조회 |
| 주문·이용 권한·무료 이용 등록·계정 역할 | 로그인한 본인만 조회, 클라이언트 직접 변경 금지 |
| 결제 이벤트·상품 매핑·초대 코드·등록 시도 | 서버 전용 |
| API 키·웹훅 비밀값·관리자 키 | 서버 비밀 설정에만 보관 |

14개 테이블에 RLS가 활성화돼 있다. get_app_access()는 호출자 권한으로 실행한다. 새 postgres 소유 함수와 public 테이블은 명시적 권한 없이 클라이언트에 개방하지 않는다. 다른 역할이 생성하는 객체에도 별도 기본 권한 설정이 필요하다. 서버 관리자 키는 RLS를 우회하므로 사용자·상품·Test/Live 환경을 서버에서 검증한다.

앱 refresh credential은 OS 보안 저장소를 사용하고 웹 세션은 sessionStorage를 사용한다. 비밀값을 저장소·앱·웹·문서·로그에 넣지 않는다. 초대 코드는 사용자 결정에 따라 무기한·무제한 활성 상태를 유지한다. 원문 공개를 피하고 등록 실패·급증을 점검한다. 기존 권한과 신규 초대 등록 정책은 변경하지 않았다.

## 변경·키·로그 관리

1. DB 변경은 마이그레이션으로 관리한다. 새 객체의 RLS·최소 권한과 익명·본인·타 계정 접근을 함께 검증한다.
2. Test/Live 키와 웹훅 비밀값을 분리한다. 정상 교체는 새 키 등록 → 서버 반영 → 정상 요청 확인 → 이전 키 폐기 순서로 한다. 노출된 키는 즉시 폐기하고 영향 요청을 조사한다.
3. 로그에는 요청/이벤트 ID·결과·오류 분류만 남긴다. 토큰, Authorization, 초대 코드, 전체 결제 원문 및 고객 이메일을 진단 로그에 추가하지 않는다. 기존 저장 필드·접근자는 별도로 점검한다.
4. 웹 배포 전 npm run check:security와 npm test를 실행한다. 탐지기는 알려진 키 형식과 파일만 검사하므로 전체 Git 이력이나 모든 비밀값의 부재를 보증하지 않는다.

## 백업·복구 설계 — 설정 확인 필요

실제 백업 플랜, PITR 활성화, 보존 기간, 복구 성공은 이번 작업에서 확인하지 않았다. 다음은 적용 완료가 아닌 운영 목표 초안이다.

- 일일 DB 백업과 별도 암호화 보관을 목표로 한다. RPO 24시간·RTO 4시간은 규모·비용 확인 후 확정한다. 더 짧은 RPO가 필요하면 PITR 지원 플랜과 비용을 확인한다.
- 백업 접근자를 최소 운영 관리자로 제한하고 MFA를 적용한다. 암호화 키를 백업 파일과 분리한다. Storage 파일과 서버 설정·비밀값 복구 절차를 별도로 준비한다.
- 분리된 프로젝트에서 복구 훈련을 수행하고 데이터 수·주문/권한 정합성·RLS·함수 권한을 검증한다. 복구 환경에서는 실제 결제 호출을 차단한다.
- 주문·결제 증빙의 법적 보존 요구와 등록 시도·오류 로그의 최소 필요 기간을 확인한 뒤 보존 정책을 확정한다. 이번 작업은 데이터를 삭제하지 않았다.

## 사고 대응과 남은 확인

노출 경로 확인 → 관련 키 폐기·최소 범위 차단 → 감사 근거 보존 → 영향 계정/주문 파악 → 안전한 설정 복구 → 재발 방지 검증 순서로 처리한다. 운영 데이터 덮어쓰기나 초대 코드 중지는 영향을 확인한 뒤 결정한다.

Supabase leaked password protection 경고가 남아 있다. 현재 앱은 Google 로그인을 사용하지만 프로젝트 전체 이메일/비밀번호 인증 설정과 보호 기능 활성화는 별도 확인이 필요하다. 웹 헤더는 소스·dry-run 검증까지 완료했고 공개 반영·브라우저 OAuth/결제/CSP 확인은 남아 있다.
