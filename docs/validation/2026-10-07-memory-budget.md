# macOS 앱 메모리 최적화 현재까지의 결과

사용자 요청에 따라 3D 추가 최적화를 마무리하고 현재까지의 변경·검증을 보고한다.
최종 소스의 기능 검사와 짧은 Retina 측정까지 확인하며, 정식 전체 시간·30분 반복 실행은 수행하지 않았다.
따라서 모든 사용 흐름에서 400MB 미만을 달성했다고 판정하지 않는다.

## 측정 계약

400MB는 **400,000,000바이트**로 판정한다. `.NET managed heap`이나 RSS만 낮다고 통과시키지 않는다.
macOS ARM64 / macOS 26.6.2 / .NET 10.0.12 / Avalonia 12.1.2의 실제 네이티브 Release 실행에서
200ms마다 RSS, physical footprint(압축된 메모리 비용 포함), 커널의 프로세스 생애 최고값,
관리 힙·GC 횟수·누적 할당을 기록했다. 최종 실행기는 CPU 누적 시간도 기록한다.
한 실행의 시간 샘플은 서로 연관되므로 표본 백분위는 관찰값이며 통계적 모집단 보장은 아니다.

실행별 새 `UNFOLD_DATA_DIR`를 사용하고 전후 바이너리·자산을 별도 고정했다.
실행기가 선택한 제품 DLL을 명시적으로 복사하고 SHA-256 일치를 검사한다.
초기 짧은 변경 후 실행에서 MSBuild가 이전 참조 DLL을 재사용한 사례를 발견해 해당 결과는 판정에서 제외했다.
강제 GC·힙 상한·프로세스 종료로 메모리 수치를 줄이지 않았다.
별도 자동 검사의 `GC.Collect()`는 atlas 참조 해제·손상 파일 복구를 검증하는 단위 검사에만 사용했다.

모의 복원 계정·구매 권한으로 정상 `AppRuntime.Start()`를 호출하고 UI 명령을 자동으로 실행했다.
네이티브 창과 실제 렌더러를 사용하지만 운영 OAuth·서버 통신·물리 포인터 입력을 검증한 것은 아니다.

## 변경

- `AnimationView`는 전체 프레임 수만큼 native bitmap을 만들던 방식에서 현재 프레임용 `WriteableBitmap` 1개를 재사용한다.
  2D 화질·프레임 시간·투명도·핑퐁·완료 이벤트를 유지하며 GLB의 기존 이중 렌더링 버퍼 계약을 유지했다.
- 완료 클립의 강한 캐시를 32MiB로 제한하고 디코딩을 직렬화한다. 큰 활성 클립은 약한 참조로 공유하고 숨긴 홈 미리보기를 해제한다.
  캐시 완료·Clear 경합, 실패/취소 후 재시도, 실패 메타데이터 32개 제한을 포함한다.
- 스프라이트 타임라인의 같은 셀은 픽셀 배열을 공유한다. 전체 atlas는 약한 참조로 보관한다.
  최초 검증한 첫 셀 snapshot은 보관해 PNG가 나중에 없어져도 알림·홈의 정지 이미지 복구가 파일 IO 없이 동작한다.
  atlas를 다시 읽을 때 manifest 크기도 다시 검사한다.
- 동일 GIF 콘텐츠는 SHA-256 기반 약한 프레임 참조를 공유한다. 제작 초안의 썸네일·내보내기는 첫 프레임 snapshot을 사용해 전체 GIF를 다시 디코딩하지 않는다.
  공유 소스 픽셀은 읽기 전용으로 사용하고 편집에는 복사본을 사용한다.
- GLB 캐시 확인과 자산 감사의 해시는 스트리밍으로 계산해 반복 검증마다 전체 파일 배열을 만드는 할당을 제거했다.
  파일 크기 제한·콘텐츠 기반 identity·실제 패키지 검증은 유지했다.
- 캐릭터 팩의 Create/Open/CopyTo는 ZIP·파일 전체 복사본을 동시에 보관하는 대신 비공개 파일 snapshot을 스트리밍으로 만든다.
  16KiB 복사 버퍼와 증분 SHA-256을 쓰며 선언/실제 길이·총량·메타데이터·중복·링크·체크섬·동일 배포본 검증을 유지한다.
  검증 후 원자적으로 게시하고 실패 시 임시 파일을 정리한다. 저장·설치 반환값에도 검증된 정지 이미지를 전달한다.
- 첫 정식 최적화 실행은 408.18MB까지 올라가 기준을 초과했다. GC가 사용하지 않는 힙 공간을 보관하는 비용도 줄이도록
  제품 호스트에 `System.GC.ConserveMemory=7`을 적용했다. Microsoft가 권장하는 시작 범위(5~7) 중 하나이며
  더 잦은 수집·LOH 압축과 잠재적 pause 비용을 갖는 정책이다. [공식 GC 설정 문서](https://learn.microsoft.com/en-us/dotnet/core/runtime-config/garbage-collector#conserve-memory)
  실행기에도 **선택한 제품 runtimeconfig의 정책을 동일하게 적용**하고 실제 GC 설정 값을 기록한다.
  400MB 프로세스/힙 강제 상한을 설정한 것은 아니다.
- Retina 2x에서 빠른 전환 중 416.84MB를 추가 관찰해 `SkiaOptions.MaxGpuResourceSizeBytes`를 4MiB로 제한했다.
  재사용 그래픽 리소스 캐시의 정책이며 활성 화면과 실제 렌더링 해상도를 줄이지 않는다.
  [공식 Avalonia 캐시 옵션](https://api-docs.avaloniaui.net/docs/P_Avalonia_SkiaOptions_MaxGpuResourceSizeBytes)
  측정 도구는 제품의 `Program.ConfigureRendering()`을 직접 재사용하고 선택한 화면의 실제 배율을 확인한다.
  이후 2배 빠른 전환에서 441.80MB 초과를 재현해 패키지 중간 복사본도 제거했다.
  격리된 GC9 실험은 471.65MB로 개선되지 않아 제품에 적용하지 않았다.
- 스트리밍 뒤에도 OpenGL 2배 빠른 전환은 447.07MB, GIF는 406.93MB로 초과했다.
  소프트웨어 합성 실험은 대표 흐름의 physical418.28MB·RSS432.28MB로 기준을 넘었다.
  따라서 이 실험과 GC9는 채택하지 않았으며 macOS의 기존 OpenGL 우선·소프트웨어 fallback을 복원했다.
  GLB 모델의 CPU 렌더링·안티앨리어싱·프레임 시간·픽셀 크기를 유지한다.
  Retina 창의 실제 배율과 GLB 150%의576px 출력도 측정기에서 확인했다.

## 적용·검증 경계

원본 자산·사용자 데이터·다른 작업트리의 변경을 보존했다. 설치 앱이나 공개 배포본을 교체한 작업은 아니다.
실제 Windows 실행·설치 업데이트와 네이티브 화면 표시 FPS는 검증하지 않았다.
GLB의 임의 대형 texture/morph 입력·동시에 보관하는 임의 외부 파일 수·다른 OS 환경 전체에 대한
절대 프로세스 상한은 고정 입력의 측정만으로 보장하지 않는다. 지원 입력 자체를 축소하거나 파일 화질을 낮추지는 않았다.
