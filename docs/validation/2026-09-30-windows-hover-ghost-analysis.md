# Beta v1.0.0 — Windows 펫 호버 시 잔상 원인 분석

2026-09-30. 요청 범위는 원인 분석이다. 제품 코드·리소스·기존 문서·배포 파일은 변경하지 않았다.

## 결론

가장 유력한 원인은 **호버 말풍선을 펼칠 때 동일한 투명 네이티브 창의 크기·내부 배치·화면 위치를 변경하는 과정과 Windows 화면 합성 시점의 불일치**다. 새 배치가 화면에 반영되기 전에 이전 펫 그림이 잠깐 표시되거나 겹쳐 남는 경로가 의심된다.

창 전환 구조와 Windows 기본 렌더링 경로는 확인했다. 사용자가 본 잔상이 실제로 어느 렌더링 단계에서 생기는지는 Windows 실기 녹화·렌더러 로그가 없어 아직 확정하지 못했다. 특정 GPU 드라이버나 Avalonia 자체 결함으로 단정할 근거는 없다.

## 배포본 기준 확인

- 대상: 공개 `v1.0.0-beta`의 `Unfold-v1.0.0-beta-win-x64.zip`.
- ZIP: 106,302,012 bytes. SHA-256: `2b25a01186317c15a55b251efbde8db34ee37f09852ad93b1040bd340a54f544`.
- 로컬 ZIP의 해시가 이전 전체 웹 다운로드 검증 및 Beta 자산 감사와 일치한다.
- `artifacts/access-code-qa/source-inputs.json`의 빌드 입력 해시와 현재 `PetWindow.cs`, `PetSpeechBubble.cs`, `AnimationView.cs`, `Program.cs`, `PetWindow.Companion.cs`, `PetWindow.PointerArt.cs`, `AppRuntime.cs`, 프로젝트 파일이 일치한다. 배포본과 다른 새 소스를 분석한 결과가 아니다.
- ZIP의 `Unfold.deps.json`은 Avalonia·Avalonia.Win32 `12.1.2`를 사용한다. 배포 DLL은 ReadyToRun 형식이므로 NuGet의 원래 DLL과 단순 파일 해시 비교로 동일성을 판단하지 않았다.
- 공식 NuGet의 소스 커밋은 `d3c867a9e2de379249b03dbeb3495bd7f076a81a`다. 해당 커밋의 Windows 옵션·창 구현·레이아웃 관리 코드를 교차 확인했다.

### 전환 크기와 좌표

다음 값은 펫 100%, 화면 배율 100%, 화면 중앙에 충분한 공간이 있을 때 코드 공식으로 계산한 값이다. 가장자리에서는 방향 전환·교차축 보정이 추가될 수 있다.

| 말풍선 방향 | 호버 전 창 | 호버 후 창 | 펫 내부 좌표 | 창 원점 이동 |
| --- | --- | --- | --- | --- |
| 위 | 192×192 | 240×300 | (24, 108) | (-24, -108) |
| 아래 | 192×192 | 240×300 | (24, 0) | (-24, 0) |
| 왼쪽 | 192×192 | 444×192 | (252, 0) | (-252, 0) |
| 오른쪽 | 192×192 | 444×192 | (0, 0) | 없음 |

즉, 화면상의 펫 위치를 유지하는 계산이 맞더라도 **창의 크기를 바꾸는 과정 자체는 모든 방향에서 발생**한다. 이전 창 그림과 새 내부 좌표가 서로 다른 시점에 화면에 반영되면 잔상이 생길 여지가 있다.

## 확인된 사실과 추정의 구분

### 확인된 사실

1. **펫과 시계는 같은 투명 Window에 있다.** 생성자에서 하나의 Canvas에 애니메이션·말풍선·꼬리를 추가한다. 호버 표시를 위해 펫 Window 자체를 확장한다.
2. **기존 수정은 논리 배치 순서를 맞춘다.** `UpdateLayout()`을 먼저 호출하지만, 이 호출은 GPU의 새 프레임 제출·Windows 화면 합성 완료를 기다리는 장치가 아니다. 공식 `LayoutManager.ExecuteLayoutPass()`는 measure/arrange를 수행하고 Windows 렌더 타이머는 별도 경로로 동작한다.
3. **Windows의 렌더링 호환 조정은 따로 없다.** `Program.ConfigureRendering()`의 기존 잔상 대응은 macOS에서 OpenGL을 우선하도록 설정하는 부분이다. Windows는 기본 렌더링 옵션을 사용한다.
4. **Windows에서는 별도 입력 전환이 있다.** 40ms 타이머가 포인터를 확인하고 `WS_EX_TRANSPARENT` 비트를 변경한다. 호버 창 배치 전환과 같은 구간에 네이티브 스타일 변경이 일어날 수 있다. 이것이 잔상의 직접 원인이라는 증거는 아직 없다.
5. **시계 갱신마다 창을 반복 확장하지 않는다.** `AppRuntime`의 1초 Tick은 시계를 새로 표시하지만, `RefreshSpeech()`는 레이아웃이 같으면 Width·Height·Position 변경 전에 반환한다. 주요 조사 구간은 첫 호버 확장과 호버 종료 축소다.
6. **호버 처리에는 펫 두 장을 중복 렌더링하는 코드가 없다.** `AnimationView.Render()`는 현재 비트맵 한 개를 그린다. 일반 idle 상태의 호버는 클릭·들어 올리기 프레임을 새로 재생하지 않는다. 자산 교체보다 창·합성 전환을 먼저 조사할 근거다.

Windows 기본 옵션은 ANGLE EGL → Software이고, 합성 옵션은 WinUIComposition → DirectComposition → RedirectionSurface 순서다. 이는 초기화 실패 시의 후보 순서이며, 사용자의 PC가 실제로 어느 경로를 선택했는지는 수집하지 않았다. [배포 버전의 공식 Windows 옵션 소스](https://github.com/AvaloniaUI/Avalonia/blob/d3c867a9e2de379249b03dbeb3495bd7f076a81a/src/Windows/Avalonia.Win32/Win32PlatformOptions.cs)

### 가장 유력한 추정

투명 창이 확장·이동하는 순간, Windows가 합성 중인 이전 표면과 새 Avalonia 프레임의 반영 순서가 어긋나 일시적으로 이전 실루엣을 보여주는 현상이다. 이후 프레임 반영으로 사라지는 사용자 설명과 맞는다. 기존 macOS 수정만으로 Windows의 이 경로를 검증한 것으로 볼 수 없다.

보조 조사 대상은 Windows 클릭 통과 스타일 전환, 화면 배율·모니터 변경, 화면 가장자리의 말풍선 방향 변경이다. 펫 랜덤 행동과 동시에 발생했는지도 실기 기록으로 분리해야 한다.

## 자동 검사 결과

검사는 이 Mac에서 Avalonia Headless + Skia로 실행했다. 실제 Windows DWM·GPU·마우스 입력의 검증이 아니다. 데이터 폴더는 매번 새로운 임시 `UNFOLD_DATA_DIR`을 사용했다.

```sh
dotnet test tests/Unfold.Tests/Unfold.Tests.csproj -c Release --no-restore --no-build \
  --filter 'FullyQualifiedName~PetHoverTests|FullyQualifiedName~AnimationRenderingTests'
```

| 검사 | 결과 |
| --- | --- |
| 배포 ZIP 해시 및 관련 소스 입력 비교 | 일치 |
| 호버·애니메이션 집중 검사 | 20개 중 19 통과 / 1 실패 |
| 실패한 호버 직후 누름·드래그 검사 단독 실행 | 1개 중 1 실패 |
| Windows 실기 잔상 재현 | 미수행 |
| 새로운 macOS 물리 입력·네이티브 잔상 촬영 | 미수행 |

실패 사례는 `PetHoverTests.PressBeforeQueuedHoverLayoutDoesNotJumpWhenDraggingStarts`다. 예상 원점 `(525, 400)`에 대해 집중 실행은 `(527, 410)`, 단독 실행은 `(526, 404)`를 기록했다. **호버 후 누름·드래그 좌표 검사에서 재현된 별도 문제**이며, 클릭하지 않은 Windows 호버 잔상을 재현했다고 해석하지 않는다. 검사 입력이 `PetView.TranslatePoint()`를 사용하고 실행 중인 자세 타이머가 변형을 갱신할 수 있으므로, 테스트의 좌표·시간 의존성과 제품 드래그 동작을 후속 조사에서 분리해야 한다.

펫 5종의 이전 실루엣 정리 검사는 통과했지만, 해당 검사는 흰색 배경·고정 크기 창에서 렌더링한다. 투명 Windows 창 확장 중의 이전 합성 표면 유지 여부를 검사하지 않는다. 기존 좌표 회귀 검사 역시 PositionChanged 순간의 배치를 확인하며 화면에 표시된 중간 픽셀을 확인하지 않는다.

첫 제한 환경 실행은 테스트 실행기의 localhost 통신 소켓 권한 때문에 중단됐고, 소켓이 가능한 환경에서 위 실제 검사 결과를 얻었다. 테스트 실행 환경 오류와 제품 실패를 구분한다.

근거: `artifacts/validation/2026-09-30-windows-hover-analysis/analysis-evidence.json`, `hover-rendering.trx`, `queued-hover-drag-isolated.trx`. 공식 Avalonia 소스 사본도 같은 증거 폴더에 있다.

## 수정 후보와 파일 소유권

수정은 이번 요청 범위에 포함하지 않는다. 아래 순서로 원인을 확인한 뒤 구현 범위를 정하는 것이 적절하다.

| 우선순위 | 후보 작업 | 주 대상 | 수용 기준 |
| --- | --- | --- | --- |
| P1 | Windows 네이티브 호버 전환을 녹화하고 창 크기·Position·펫 내부 좌표·실제 렌더러·스타일 변경을 함께 기록 | 별도 진단 하네스, `PetWindow.cs`, `Program.cs` | 잔상이 생긴 화면 프레임과 전환 이벤트를 대응할 수 있음 |
| P1 | 같은 Windows PC에서 기본 GPU 경로와 소프트웨어 경로를 진단용으로 비교 | 별도 진단 빌드의 AppBuilder 설정 | 소스·펫·DPI·위치 조건을 유지하며 잔상 유무를 비교. 앱 전체 소프트웨어 강제 전환을 곧바로 배포하지 않음 |
| P1 | 호버 표시가 펫 네이티브 창의 크기·위치를 바꾸지 않는 구조, 또는 네이티브 배치와 새 프레임 반영을 일관되게 처리하는 방식을 검토 | `PetWindow.cs`, `PetSpeechBubble.cs` | 첫 진입·이탈 때 이전 펫 실루엣이 표시되지 않으며 기존 말풍선·드래그·클릭 통과 유지 |
| P2 | 새로 실패한 누름 직후 드래그 검사에서 변형 좌표·자세 타이머 영향을 분리 | `PetHoverTests.cs`, `PetWindow.cs` | 고정 화면 이동량과 기대 원점을 안정적으로 비교하고 실기 드래그에서도 일치 |

자산 재생성, 타이머 속도 증가, 시계 제거, 전체 앱의 렌더러 변경은 현재 근거로 필요한 수정이라고 판단하지 않는다.

## Windows 확인 순서와 미검증 항목

1. 해당 ZIP으로 첫 호버 진입·이탈을 클릭 없이 반복한다. 기본 펫 5종, 말풍선 네 방향과 화면 중앙·가장자리를 구분한다.
2. 펫이 기본 idle일 때와 랜덤 행동 중일 때를 분리한다. 잔상이 정상 펫과 겹치는지, 이전 창 원점 쪽에 나타나는지 기록한다.
3. Windows 버전·GPU·배율(100/125/150%)·단일/다중 모니터·실제 렌더러를 기록하고 프레임 단위 영상으로 확인한다.
4. 기본 렌더링과 진단용 소프트웨어 렌더링, 클릭 통과 스타일 전환을 억제한 진단 조건을 비교해 창 전환·GPU·입력 스타일의 영향을 분리한다.
5. 원인 대응 후 같은 조건에서 첫 호버·반복 호버·클릭·누름 유지·드래그·실제 스트레칭 말풍선까지 회귀 확인한다.

현재 Windows 실행 환경을 사용할 수 없어 이 순서의 실기 검증과 실제 수정 효과는 확인하지 않았다.
