## 원인

기존 Retina 배율 보정은 이미 적용되어 있었다. 현재 코드에서 창 위치 계산은
`DesktopScaling`을 사용하므로 과거의 `RenderScaling` 중복 배율 문제를 다시 수정하지 않았다.

이번에 확인한 경로는 다음과 같다.

1. 드래그를 놓는 순간 `ClampPosition()`이 Dock을 제외한 `Screen.WorkingArea`에
   **펫과 말풍선을 합친 창 전체**를 강제로 맞췄다.
2. 호버·휴식 알림이 열리거나 크기가 바뀌면 `layout.Position()`도 창 전체를 작업 영역에 맞췄다.
   호버는 방향을 바꿀 수 있었지만 Dock 밖 작업 영역에 펫 자체가 있으면 기준 좌표를 보존하지 못했다.
3. 휴식 중 자동 이동도 같은 창 크기와 작업 영역을 사용해 첫 이동에서 위치를 크게 보정할 수 있었다.

수정 전 네이티브 창에서 아래쪽 알림을 열었을 때 펫 원점이 `(800, 888)`에서
`(800, 717)`로 바뀌었다. 같은 위치에서 `ClampPosition()`을 직접 호출해도
171포인트 위로 이동했다. 이는 macOS 자동 숨김 Dock 환경에서도 말풍선 크기 때문에
이동할 수 있음을 보여준다. 사용자의 Mac mini에서 측정한 값은 아니다.

## 수정 계획과 적용

1. macOS의 사용자 배치 경계를 화면 전체에서 메뉴 막대만 제외한 영역으로 정한다.
   Dock의 아래·왼쪽·오른쪽 위치와 자동 숨김 여부가 사용자가 놓은 좌표를 밀어내지 않게 한다.
2. 놓기 시 펫 사각형만 화면 안으로 제한한다. 말풍선이 들어갈 자리를 확보할 때는
   가능한 방향으로 바꾸거나 가로·세로 정렬을 조정해 펫 원점을 유지한다.
3. macOS 휴식 중 이동은 펫 원점과 펫 크기를 기준으로 진행하고, 말풍선 배치를 함께 갱신한다.
4. Windows의 기존 작업 영역과 모니터 선택 규칙, 기본 생성 위치, UI 문구와 요소는 유지한다.
5. 4K 논리 해상도·다중 모니터 원점·Dock 위치·펫 크기의 회귀 검사와 실제 macOS 좌표 측정을 수행한다.

## 실제 macOS 확인

검증 호스트는 MacBook Air M2이며, 외장 화면의 네이티브 좌표는 1920×1080,
내장 Retina 화면은 1470×956이었다. 현재 Dock은 자동 숨김 상태였다.
사용자 설정과 배포 앱 데이터를 사용하지 않는 별도 하네스에서 일반 펫 창 생성 경로를 실행했다.

- 두 모니터 × 펫 크기 50·100·150% × 말풍선 네 방향 × 초대·휴식·완료:
  72개 네이티브 사례에서 화면 아래쪽 펫 원점이 유지됐다.
- 실제 창의 `RenderScaling` 1·2에서 `PetAnchor`와 `PointToScreen()`으로 읽은
  펫 원점이 일치했다. 창 위치 계산의 `DesktopScaling`은 1이었다.
- 각 배치의 제한 처리와 저장 좌표를 확인했다.
- Retina 화면 아래쪽 `(2500, 764)`에서 휴식 후 자동 이동이 시작했다.
  첫 원점은 `(2501, 763)`이며 47개 이동의 최대 축 변화는 1포인트였다.
- CUA 드래그 후 수집한 화면 안의 해제 이벤트 두 쌍은 놓기 전·후 펫 원점이 일치했다.
  입력 중 다른 포인터 이벤트도 발생했으므로, 요청한 드래그 이동량이나 경로의 정확성은
  통과 근거로 사용하지 않았다.
- 검증 창을 종료했으며 실제 사용자 데이터를 변경하지 않았다.
